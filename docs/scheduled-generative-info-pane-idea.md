# 定期実行と生成 UI による情報ペインのアイデア

記録日: 2026-10-04

ステータス: アイデア。実装・採用は未決定。

## 目的

ユーザーがすでに MCP や Agent Skills を設定しているエージェント CLI を利用し、必要な情報を定期的に取得して VINTAGE の情報表示ペインに集約する。

ユーザー自身が API の取得処理や画面を実装せず、「いつ・どの情報源や手順を使い・何を取得し・どう表示するか」を指示して使える機能を目指す。API の利用に実装が必要な独自サービスや社内システム、複数サービスをまとめた個人用レポートなどを想定する。

背景として、汎用プラグイン基盤やマルチエージェントのオーケストレーションは現時点では保留とした。既存 CLI・ブラウザで十分なサービスを個別に再実装するより、ユーザーの既存 MCP 接続や Agent Skills を活用する方向を検討する。

## ユーザーが設定するもの

crontab のような日時指定とプロンプトを、一つの実行設定として登録する。

| 項目             | 内容                                                             |
| ---------------- | ---------------------------------------------------------------- |
| 名前             | 実行設定と情報ペインを識別する名前                               |
| 実行日時         | 定期実行のスケジュール。cron 式や日時選択 UI は未決定            |
| タイムゾーン     | スケジュールの基準となる地域                                     |
| エージェント CLI | 使用する実行ファイルとプロファイル、必要な作業ディレクトリ       |
| 利用する機能     | 情報取得に利用する MCP、Agent Skills、CLI ツールなど。指定は任意 |
| プロンプト       | 取得内容、集計方法、表示方法の指示                               |
| 表示先           | 結果を表示する情報ペイン                                         |

設定例:

```text
名前: 朝の情報
実行日時: 毎日 08:00
タイムゾーン: Asia/Tokyo
CLI: Codex
利用する機能: 天気取得 Skill、カレンダー MCP
プロンプト:
  今日の天気と予定を取得して。
  外出予定の時間に雨が降りそうなら目立たせて。
  OpenUI で見やすく表示して。
表示先: 朝の情報ペイン
```

## MCP と Agent Skills の位置づけ

情報取得手段は MCP に限定しない。CLI が利用できる Agent Skills、ローカルスクリプト、既存コマンドやファイルも対象にできる。

- MCP は外部サービスなどの情報・操作への接続を提供する。
- Agent Skills は情報取得、集計、整理、表示生成などの手順を提供する。Skill が MCP やスクリプトを使う組み合わせも想定する。
- VINTAGE はそれらの内部手順を実装せず、指定した CLI へプロンプトを渡して結果を受け取る。

例えば「天気 Skill で予報を取得」「利用量集計 Skill で複数 API の結果を整理」「ローカルの試験結果ファイルを集計」といった設定が考えられる。具体的に何を利用できるかは、選択した CLI とその設定に依存する。

利用する機能の指定は、プロンプトだけで CLI に選択させる方法と、MCP／Skills を明示する方法の両方を検討する。明示した機能の表示は実行方針であり、実行環境の権限制限とは区別する。

## 基本的な動作

1. VINTAGE が登録されたスケジュールを管理する。
2. 指定時刻に、選択された CLI を別プロセスで単発実行する。
3. CLI が設定済み MCP、Agent Skills、CLI ツールなどを利用して情報を取得・整理する。
4. CLI がデータと OpenUI の UI 定義を返す。
5. VINTAGE が結果を検証し、情報ペインに描画する。
6. 次回の実行時に、新しい結果で表示を更新する。

Codex を使う場合の実行イメージは `codex exec "ユーザーが指定した指示"`。実際の引数、出力形式、Skills の読み込み方、利用可能なツールの限定方法は実装前に現行 CLI の仕様を確認する。

ユーザーが操作している既存端末とは別プロセスで実行し、その端末の入力やセッションを取得処理のために変更しない。プロンプトは引数配列で渡し、シェルコマンド文字列へ連結しない。

## 表示の考え方

情報ペインは固定ダッシュボードではなく、最新の情報を表示するレポートとして扱う。

日時や取得結果によって、内容だけでなく UI の構成も変わってよい。例えば、ある日は予定表、別の日は雨の注意カードが中心になる。ユーザーの表示指示に沿って、取得の都度 UI を生成する。

OpenUI を使う場合は、VINTAGE がカード・表・グラフなどの利用可能なコンポーネントを提供し、エージェントがその組み合わせを生成する。任意の JavaScript やシェルコードを UI として実行する設計にはしない。

外枠には、生成内容とは独立して次の情報・操作を配置する案とする。

- ペイン名、最終取得日時、次回実行日時。
- 実行中・成功・失敗の状態。
- 手動更新、一時停止、指示の編集。
- 過去の実行結果を見返す履歴。

生成中は前回の成功結果を表示し続け、新しい結果の検証成功後にまとめて切り替える。失敗時は前回の結果を残し、古い情報であることと更新エラーを表示する。過去の履歴を閲覧中は、新しい結果が届いても自動で表示を切り替えない。

## VINTAGE と CLI の役割

| VINTAGE                      | エージェント CLI                  |
| ---------------------------- | --------------------------------- |
| 設定とスケジュールの保存     | MCP・Skills・ツールによる情報取得 |
| 単発プロセスの起動・停止     | ユーザー指示に沿った集計・整理    |
| タイムアウト、重複実行の防止 | 表示用データと UI 定義の生成      |
| 出力の検証と描画             | 取得不能などの結果報告            |
| 実行履歴と最終成功結果の保存 | CLI 側の認証・権限の適用          |

VINTAGE がサービスごとの API や認証をすべて実装するのではなく、ユーザーが設定済みの CLI 環境を再利用する。ただし、CLI ごとの設定読み込み、非対話実行、結果取得方式を吸収する接続層は必要になる。

## 実装時に確認すること

- **対象 MCP の限定:** プロンプトで対象を指示するだけでは利用可能な MCP を制限できない。選択した MCP だけを単発実行へ提供できるか、CLI ごとに確認する。既存設定を勝手に書き換えない。
- **Skills の読み込み:** 単発の非対話実行でも指定した Skill が認識されるか、呼び出し方、補助スクリプトの配置、作業ディレクトリへの依存を確認する。
- **読み取り権限:** 初期版は情報取得を中心にする。読み取り専用の指示だけでなく、可能なら CLI、MCP、実行するスクリプトやツール側の権限でも制限する。Skills の指示自体を権限制限とは扱わない。
- **無人実行:** 認証期限切れや承認待ちを検出し、実行を永久に待たせずユーザーへ状態を示す。
- **出力契約:** データ・UI 定義・取得日時・エラーをどう受け取るかを決める。ログと表示用出力を区別し、壊れた出力で成功結果を置き換えない。
- **生成 UI の検証:** 利用可能なコンポーネント、出力サイズ、リンクやアクションの扱いを定義する。初期版の外部更新操作は対象外とする案。
- **実行管理:** 同じ設定の重複起動を防ぎ、タイムアウト、停止、再試行回数、全体の並行数を管理する。
- **実行コスト:** 定期実行ごとに推論や API 利用が発生するため、更新間隔と実行履歴を確認できるようにする。
- **保存範囲:** 取得データや履歴の保持期間、削除方法を決める。認証情報を実行履歴へ保存しない。

## 実行場所の選択肢: クラウドでの無人実行

無人実行時のローカル端末への影響を抑えるため、実行場所をローカル CLI だけに固定せず、Codex Cloud などのクラウド実行も候補にする。VINTAGE はスケジュール、タスク投入、進捗確認、結果取得、UI の検証・表示を担当し、情報取得・集計・UI 定義生成をクラウド側で行う。

公式情報を確認した日: 2026-10-04。以下は接続方式の候補であり、VINTAGE との動作確認は未実施。

- Codex CLI の `codex cloud exec` はクラウドへのタスク投入、`codex cloud list` は状態確認の入口として案内されている。投入コマンドの終了とクラウド処理の完了は分けて管理する。構造化データや OpenUI 定義を取得する方法は別途検証が必要で、コード差分の適用を結果取得の前提にしない。
- Codex Cloud の各新規タスクは公開済み環境から独立したワークスペースを作る。ローカル環境の保護には有効だが、接続した外部サービスへの操作権限やクラウドへのデータ送信は別に管理する。
- リポジトリ内の Skills はクラウドタスクで利用できるが、ローカルの個人用 Skills は自動同期されない。必要な Skill と補助スクリプトは、利用するクラウド環境で提供する方法を決める。
- ローカル CLI に設定済みの MCP や認証が、そのままクラウド側へ引き継がれるとは扱わない。利用するクラウド実行経路での MCP／プラグイン対応と認証方法を確認する。
- リモート MCP はクラウド側での接続・認証を確認する。ローカルの stdio MCP は、クラウド環境への配置や、対応する実行経路での Secure MCP Tunnel 利用を検討する。トンネルの一般的な Codex 対応だけで、特定の `codex cloud exec` タスクで使えるとは断定しない。
- Secure MCP Tunnel は、私設ネットワーク内のクライアントから外向き HTTPS 接続を使う仕組み。トンネル側の稼働が必要で、接続先 MCP がローカル資源を操作できる場合はその影響も残る。
- ローカルコンテナ内の CLI 実行も中間案になる。ただしホストの書き込み可能なバインドマウントは、コンテナからの変更がホストへ反映される。コンテナ化だけでホストへの書き込みがなくなるとは扱わない。

実行設定には「実行場所」と「環境／プロファイル」を追加する案とする。ローカルとクラウドで同じ結果形式を返せるようにし、クラウド実行に失敗した場合にローカル実行へ自動で切り替えない。

また、処理をクラウドへ移すことと、スケジュール管理をクラウドへ移すことは別である。VINTAGE が日時を管理する構成では、アプリ終了中に新しいタスクを投入するための常駐処理や別のスケジューラが必要になる。

## スケジュールについての未決定事項

- cron 式を直接入力するか、日時選択 UI を提供するか。
- VINTAGE 終了中も動かすか。動かす場合は、常駐処理や OS のスケジューラとの連携が必要。
- スリープや終了中に実行時刻を逃した場合の扱い。
- タイムゾーン変更や夏時間の扱い。
- プロセス終了後、アプリ再起動後にどこまで状態を復元するか。

初期案は「VINTAGE 起動中に実行し、休止中の取りこぼしは再開時に最新の一回だけ実行」。これは提案段階であり、確定仕様ではない。

## 初期版の候補

対応 CLI を一つに絞り、次の一連の流れを検証する。

1. 日時・プロンプト・利用する機能・表示先を登録する。
2. 手動実行と定期実行で、CLI から情報を取得する。
3. OpenUI による結果をペインに表示する。
4. 成功時に表示を更新し、失敗時は前回の表示を保持する。
5. 実行履歴を確認し、設定を停止・編集・削除する。

サービス別のプラグイン配布基盤や、複数エージェント間のタスク割り当ては、このアイデアの初期範囲に含めない。
